# M3 P3(b) — rematch on the wire + the button

**Date:** 2026-09-09 · **Milestone:** M3 · **Phase:** P3(b)
**Anchor:** P2(a) shipped the panel set; P3(a) shipped the victory banner. The room
server has had `Room.rematch(newSeed)` since M2 (room.ts:451) but it was deliberately
kept OFF the wire (server.ts:21 "no client message can call it"; review #9 flagged the
`#endedSent` latch must reset if it ever ships). This plan ships it, with the
host-authority ruling the v1 deferral asked for.

## Host-authority ruling (parent, locked before dispatch)

**Seat 0 IS the host.** Already encoded: `RoomOptions.hostName` seeds seat 0's name
(room.ts:153), and room.ts:222's lobby comment says "host starts". v1 ruling:
- A `rematch` client message is honored ONLY from the socket whose claimed seat is 0.
- Any other seated socket gets `error { code: "notSeated" }`? NO — wrong code, lying.
  Add wire error code **`notHost`** (WireErrorCodeSchema, protocol.ts:166 — verified:
  nothing pins the enum's contents elsewhere). Spectators (seat null) also get notHost.
- **Rematch requires phase === "ended".** Mid-game refusal gets a SECOND new code,
  `badPhase` — reusing badMessage would lie (that's the parse-failure code; honest
  codes are cheap in v1). Rationale for requiring ended: the lobby has no
  kick/restart semantics yet; mid-game restart is a future product decision, not a
  wire oversight.

## Design

1. **protocol.ts**: `RematchMsgSchema = { type:"rematch" }` strict, added to
   `ClientMsgSchema`; `WireErrorCodeSchema` + `"notHost"` + `"badPhase"`. Version bump?
   PROTOCOL_VERSION lives out-of-band (server.ts:18 "both sides ship the same build")
   — no handshake in v1, so no bump; grep to confirm it's a plain const nobody pins.
2. **room.ts**: `rematch()` GAINS a return contract `{ ok: true; seed: number }`
   (or stays void + a `room.seed` getter — child picks, tests pin determinism):
   newSeed derived INTERNALLY as a deterministic function of (oldSeed, serverSeq)
   — e.g. xorshift-mix. No client may pick the seed: that is why RematchMsg carries
   nothing and the RNG stays the server's private story (M2 wireScrub law).
   Seats/tokens/names survive (already true, room.ts:449 comment).
3. **server.ts** (the crux — three hard parts, review #9 on record):
   - authority gate seat 0 (else notHost) + phase ended (else badPhase), reject
     paths unit-tested; serverSeq must NOT change on any refusal (like rejections).
   - `#endedSent = false` on successful rematch (M2 quality-review #9 debt: "if it
     ships, reset #endedSent there" — this phase IS its shipping). Test: game 2's
     winner gets its OWN gameEnded event (the count raced 2/5 in M2 — same class).
   - After room.rematch: ONE `#broadcastProjections()`. Every seat's stale state is
     replaced by the fresh setup projection frame (the adapter is stateless re:
     room identity — the projection simply lands). No new event kind: the fresh
     projection IS the signal (opApplied can't carry a non-op; playerJoined noise
     would confuse). Consequence checked: the victory banner self-nulls when the
     new projection's winner is null (VictoryOverlay derivation, P3(a)), and the
     adapter's welcome-clears-projection from the P3(a) batch does NOT fire here
     (no welcome on a live socket) — so there is no blank-frame window at all.
4. **cli.ts**: NO `--rematch` flag (fence creep; the M2 demo tool can drive game 1).
   The P3(c) demo harness, not cli.ts, proves game-2 play.
5. **table**: adapter `sendRematch(): boolean` (same guards as sendOp: OPEN socket,
   status playing — build it exactly like buildOpMessage: encode + send a literal
   `{ type:"rematch" }` frame);
   INTEGRATION TRAP: `.victory-overlay` is pointer-events:NONE (P3(a) chose
   click-through). A button inside it needs pointer-events:auto re-declared on the
   button itself (or the card, when a button exists). Without this the host button
   is visible and DEAD — the browser proof must CLICK it, not just find it.
   VictoryOverlay gains a "Start rematch" button **only when seat === 0** (client-side affordance; the SERVER is the authority — a forged
   rematch from seat 2 gets notHost; UI just doesn't dangle a dead button); other
   seats see "Waiting for the host to start a rematch…" (sub copy updates — REMATCH_COPY
   in victoryView.ts becomes seat-aware: {isHost ? button : copy}).
   Pure fn extension `victoryView(..., isHost)` → `canRematch: boolean`. Tests update.
6. **room.test/server.test/table ui tests**:
   - server.test: seat 0 can rematch after end (fresh projection serverSeq > old,
     phase "setup", winner null); seat 1 gets error notHost; spectator gets notHost;
     mid-game seat 0 gets badPhase; **gameEnded fires AGAIN in game 2** (review #9
     regression — the whole point of the latch reset).
   - room.test: rematch() new-seed determinism (same oldSeed+serverSeq → same new seed)
     and seats survive.
   - victoryView.test: canRematch only for host+winner-state; sub copy.

(no client seed anywhere on the wire).
